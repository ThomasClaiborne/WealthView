
C# / ASP.NET Core

- ENUMs in DB should match ENUM names in C#
    EF core expects direct name mapping

- null! → treat as not null
    suppress false warnings 
    shows intent that it will have a value before business logic
    EF core will populate

- Annotations on DTOs, never on models
    enforce what front end is allowed to send
    model already enforces DB structure
    [RegularExpression] → checks string against a pattern
    @ before string treats backslashes as literals 

- ApiController auto validates
    checks every annotation on incoming DTO before running method
    auto returns 400 Bad Request with error details
    mostly for request DTOs since they are coming in
    response DTOs carry data going out

- async / await / Task<T>
    async marks a method as asynchronous — it can pause and resume
    await pauses execution at that line until the async operation finishes
        without blocking the thread (server can handle other requests while waiting)
    Task<T> is the return type wrapper — like a promise that will eventually hold T
    Task<Result<AuthResponse>> means: "this will eventually give you a Result<AuthResponse>"

- Result<T> pattern
    wrapper that carries either a success payload OR an error type + messages
    every service method returns Result<T> — controller reads result.Type and maps to HTTP status
    keeps business logic errors separate from exceptions
    prevents services from throwing exceptions for expected failures (duplicate username etc.)

- BCrypt (password hashing)
    one-way hash — mathematically impossible to reverse back to the original password
    BCrypt.HashPassword(plainText) → generates a hash string like $2a$11$saltXXX...hashXXX
        $2a$ = BCrypt version, $11$ = work factor, next 22 chars = random salt, rest = hash
    BCrypt.Verify(plainText, storedHash) → re-hashes the input using the salt embedded in storedHash
        compares result to the stored hash — returns true or false
        you never decrypt — you just re-hash and compare
    work factor (default 11) = number of rounds — each +1 doubles compute time
        makes brute force attacks computationally infeasible
    salting = random data added before hashing so two identical passwords produce different hashes
        prevents rainbow table attacks (pre-computed hash lookup tables)
    plain text password never leaves the Register method after hashing

- JWT (JSON Web Token)
    a signed string the server gives the client on login — proves identity on future requests
    three parts separated by dots: header.payload.signature
        header: algorithm used (HS256 = HMAC-SHA256)
        payload: claims — data baked in (userId, username, email, expiry)
        signature: HMAC-SHA256(header + "." + payload, secretKey) — proves the server signed it
    server signs with secret key → client stores token → client sends in every request header
    server verifies signature on every protected request — if signature is valid, trusts the claims
    stateless: server stores nothing — the token is self-contained proof of identity

- GenerateToken (what it actually does step by step)
    1. reads Jwt:Secret from appsettings.json, converts to bytes
    2. SymmetricSecurityKey wraps those bytes as a cryptographic key object
    3. SigningCredentials combines the key with the HMAC-SHA256 algorithm
    4. Claims array = the payload data to embed in the token (userId, username, email)
    5. JwtSecurityToken assembles the full token (issuer, audience, claims, expiry, credentials)
    6. JwtSecurityTokenHandler().WriteToken(token) serializes it to the final dot-separated string
    NuGet dependency: Microsoft.AspNetCore.Authentication.JwtBearer (brings in token classes)
    on every protected request: JWT middleware reads the Authorization header, verifies the
        signature against the same secret, and if valid, populates User.Claims automatically

- ToAuthResponse (response mapper)
    maps the internal AppUser model + token string into the AuthResponse DTO shape
    DTOs and models are different objects — the model has PasswordHash, the DTO does not
    this pattern ensures sensitive fields on the model are never accidentally sent to the frontend

- Transaction (BeginTransactionAsync)
    wraps multiple DB operations into one atomic unit — all succeed or all roll back
    used in AuthService.Register because user + portfolio must be created together
    if portfolio creation fails after user was inserted, transaction rolls back the user too
    without a transaction, a crash between the two inserts would leave a user with no portfolio
    EF Core: BeginTransactionAsync() → do work → CommitAsync() or RollbackAsync()
    Java Dev10 equivalent: @Transactional annotation on a service method

EF Core:

- DbSet<T> is EF Core handle to a table
    equivalent to running SELECT * FROM T 
    every LINQ query translates to SQL automatically

- OnModelCreating for configuring model <→ db mapping
    had modelBuilder argument
    override definition from base class (DbContext)
    EF Core conventions often dont match schema

- FluentAPI → method chaining to define rules with modelBuilder
    each method returns builder object to chain
    EF Core cant tell which has FK with one-to-one relationships

- FirstOrDefaultAsync → queries database for first row matching condition
    async LINQ extension method by EF Core

- SaveChangesAsync → takes everything staged, generates SQL and executes against DB
    method from DbContext itself
    .Add(), .Remove(), modifications to tracked objects
    like a commit button but to the DB

- .HasColumnType("decimal(18,4)")
    tells EF Core to use MySQL's DECIMAL type with 18 total digits and 4 after the decimal point
    without this, EF Core might use float or double — both introduce rounding errors for money
    DECIMAL is exact arithmetic: 0.1 + 0.2 = 0.3 exactly, not 0.30000000000000004
    18 = total significant digits (14 before decimal + 4 after)

- .HasConversion<string>() on enum properties
    EF Core stores enums as integers by default (0, 1, 2...)
    this tells EF Core to store the enum NAME as a string instead ("Buy", "Sell")
    required so the DB value matches what MySQL ENUM column expects
    without it: DB would have 0 and 1, not "Buy" and "Sell"

- Scoped lifetime (AddScoped)
    AppDbContext is registered as scoped — one instance per HTTP request, then discarded
    every repository and service that depends on AppDbContext must also be scoped
    this is why you use AddScoped<IAuthService, AuthService>() — not AddSingleton
    AddSingleton would hold one AppDbContext forever — causes threading issues and stale data

Testing (xUnit):

- TestDbContextFactory → resuable helper class that creates configured AppDbContext pointed to test DB
    every test calls it so its not repeated every setup
    reads connection string from the test projects 

- DatabaseTestCollection → used to disable parallel execution of database tests
    CollectionDefinition declare a name for test collection over dummy class (DatabaseTestCollection)
    Collection placed above test classes 
    force multiple classes in this collection to run test in series

- IAsyncLifetime → class that async tests derive from
    has IAsyncLifetime which executes before every test (async constructor)
    has DisposeAsync that runs after (async destruct)

- Unit test vs integration test
    unit test: tests one class in isolation — dependencies are mocked (Moq)
        fast, no DB, no external dependencies
        example: AuthServiceTest — uses InMemory DB, no real MySQL
    integration test: tests against real infrastructure (real DB, real network)
        slower, requires setup (KnownGoodState)
        example: EfUserRepositoryTest — hits wealthview_test via real MySQL connection

- InMemory database (service tests)
    EF Core provider that runs entirely in memory — no MySQL required
    used for service tests because we're testing business logic, not SQL
    each test gets a fresh DB via Guid.NewGuid().ToString() as the DB name
    transactions are no-ops (commit/rollback do nothing) — fine for testing logic
    ConfigureWarnings(w => w.Ignore(InMemoryEventId.TransactionIgnoredWarning))
        suppresses the exception EF Core throws when you call BeginTransactionAsync on InMemory
        the transaction still "runs" — it just doesn't actually do anything

- KnownGoodState procedure
    stored procedure in wealthview_test that resets all data to a predictable baseline
    called in InitializeAsync() before every test
    DELETE instead of TRUNCATE (TRUNCATE has inconsistent FK behavior in MySQL 8+)
    ALTER TABLE ... AUTO_INCREMENT = 1 after deletes to reset ID counters
    explicit IDs in inserts (1, 2, 3...) so every test can assert exact IDs

Angular:

    Auth Service

        - @Injectable({ providedIn: 'root' })
            decorator that registers this class with Angular's DI container
            providedIn: 'root' = one instance created for the entire app (singleton)
            any component that calls inject(AuthService) gets the SAME instance
            without this decorator it is just a plain TypeScript class — Angular doesn't know it exists
            React equivalent: a Context value created at the App level

        - BehaviorSubject<AppUser | null>
            from RxJS — acts as both a holder of state AND a broadcaster of changes
            holds a current value at all times (starts as null = nobody logged in)
            when .next(newValue) is called → every subscriber immediately receives the new value
            React equivalent: the state inside useContext — when it changes, everything subscribed re-renders
            null = logged out  /  AppUser object = logged in

        - .asObservable()
            exposes the BehaviorSubject as a read-only Observable
            other code can subscribe and listen for changes but cannot push new values
            only the service itself can call .next() — the component just listens
            currentUser$ is the public-facing Observable — used in Sidebar to watch for changes

        - constructor()
            runs once when Angular creates the service — at app startup
            checks localStorage for a saved session (token + currentUser)
            if found: calls userSubject.next(parsedUser) to restore logged-in state
            this is session re-hydration — makes the app remember who was logged in after a page refresh

        - register() / login()
            call the API and return the Observable to the caller (they don't subscribe themselves)
            .pipe(tap(res => this.setSession(res))) — tap is a side effect
                when the call succeeds: run setSession to save token + user, then pass the response through
                the component subscribes and uses the response to navigate
            returning the Observable instead of subscribing internally
                lets the component react to success/failure and navigate accordingly
                React equivalent: returning the fetch Promise instead of awaiting it inside the service

        - setSession(res)
            private — only called by register() and login()
            extracts user fields from AuthResponse → creates AppUser (no token, no password)
            localStorage.setItem('token', ...) — interceptor reads this for every future request
            localStorage.setItem('currentUser', ...) — re-hydration reads this on page refresh
            userSubject.next(user) — broadcasts the new logged-in user to all subscribers

        - logout()
            removes token and currentUser from localStorage
            userSubject.next(null) — broadcasts logged-out state to all subscribers
            Sidebar sees this change and hides the user name block
            router.navigate(['/']) sends the user to the landing page

        - isLoggedIn()
            reads userSubject.value — synchronously gets the current value without subscribing
            returns true if a user is present, false if null
            used by guards to make routing decisions immediately

    Guard

        - CanActivateFn
            a function Angular Router calls before activating any route that uses canActivate: [...]
            return true          → allow navigation — user reaches the route
            return false         → block navigation — user stays where they are
            return UrlTree       → redirect — Angular cancels the original nav and goes somewhere else

        - router.createUrlTree(['/login'])
            creates a UrlTree — Angular Router's internal representation of a destination URL
            when returned from a guard it acts as a redirect instruction
            why not router.navigate(['/login'])?
                navigate() fires a new navigation event in parallel — can cause race conditions
                returning a UrlTree tells the Router "use THIS as the destination instead"
                Angular cancels the original navigation and follows the UrlTree cleanly

        - authGuard (protects dashboard and all authenticated pages)
            auth.isLoggedIn() returns true  → return true   → route activates, page loads
            auth.isLoggedIn() returns false → return router.createUrlTree(['/login']) → redirected

        - publicOnlyGuard (protects login, register, landing from logged-in users)
            auth.isLoggedIn() returns true  → return router.createUrlTree(['/dashboard']) → redirected
            auth.isLoggedIn() returns false → return true   → route activates, page loads

        - the || shortcut in the guard functions
            return auth.isLoggedIn() || router.createUrlTree(['/login'])
            if isLoggedIn() is true  → true || anything = true (right side never evaluated)
            if isLoggedIn() is false → false || createUrlTree → returns the UrlTree
            concise way to express "allow if logged in, otherwise redirect"

        - canActivate on MainLayout route
            applied to the parent layout, not each child individually
            all child routes (dashboard, bank-accounts, etc.) inherit the guard
            one guard protects the entire authenticated section at once

    interceptor 

        - what it does
            runs automatically on every outbound HTTP request in the entire app
            reads the token from AuthService and attaches it to the Authorization header
            no component ever manually sets auth headers — it is handled here in one place

        - HttpInterceptorFn signature
            (req, next) => Observable<HttpEvent<unknown>>
            req  = the outgoing HTTP request object
            next = a function that forwards the request to the next handler (then to the network)

        - req.clone({ setHeaders: { Authorization: `Bearer ${token}` } })
            HTTP request objects are immutable — you cannot modify them directly
            .clone() creates a copy with your changes applied
            Bearer ${token} is the format the ASP.NET JWT middleware expects in the Authorization header

        - flow of every HTTP call
            component calls HttpClient.post(...)
                ↓
            authInterceptor runs
                ↓ (if token exists)
            new request created with Authorization header added
                ↓
            next(newReq) sends it to the network
                ↓
            response comes back to the component's .subscribe()

        - if no token
            return next(req) — passes the original request through unchanged
            unauthenticated requests (register, login) go through without modification

        - registration in app.config.ts
            provideHttpClient(withInterceptors([authInterceptor]))
            registered once — applies to every HttpClient call in the entire app automatically

    AppUser Vs AuthResponse

        - AuthResponse — shape of what the backend sends back on login/register
            token, appUserId, username, email, firstName, lastName
            the token is included because the frontend needs it immediately after login

        - AppUser — shape of what we store and share across the app
            appUserId, username, email, firstName, lastName
            no token field — token is stored separately in localStorage

        - why two separate interfaces
            they represent different concerns
            token = a credential for making future requests — stored alone, read only by the interceptor
            user = identity information — stored for display (name in sidebar), guards (isLoggedIn), etc.
            mixing them would mean BehaviorSubject<AuthResponse | null> carries the token everywhere
                every component that subscribes sees the token even though they never need it
                separation of concerns — each piece of data lives where it belongs

        - setSession() splits them
            takes AuthResponse (has token)
            stores token alone → localStorage('token') → read by interceptor
            stores AppUser alone → localStorage('currentUser') → read by re-hydration + sidebar
            broadcasts AppUser → userSubject.next(user) → BehaviorSubject holds user, not the token

    Component Anatomy

        - @Component decorator
            metadata that tells Angular everything it needs to know about this component
            Angular reads this at build time to compile the component correctly

        - selector: 'app-login'
            the custom HTML tag that represents this component: <app-login />
            used when embedding one component inside another component's template
            less relevant when routes load components — routing uses the class reference, not the tag

        - standalone: true
            this component manages its own dependencies — no NgModule needed
            Angular 17+ default
            means: everything this component's template uses must be in its own imports array

        - imports: [ReactiveFormsModule, RouterLink]
            declares what this component's template needs
            ReactiveFormsModule → enables [formGroup] and formControlName attributes in the template
            RouterLink → enables routerLink="..." attribute in the template
            RouterLinkActive → enables routerLinkActive="..." attribute
            forgetting one here but using it in the template → Angular throws a compile error

        - templateUrl: './login.html'
            path to the HTML file for this component
            Angular compiles the .ts class and the .html together — they are one component at runtime
            alternative: template: '<div>inline html here</div>' — used for very simple components

        - does importing a component grab its HTML too?
            import { Login } from './auth/login'  ← imports the TypeScript class Login
            Angular sees that Login has templateUrl: './login.html'
            at build time Angular automatically includes the HTML as part of the component bundle
            you never import the HTML file separately — Angular handles that connection
            when you put Login in routes or in imports:[] — Angular uses the class as a reference
            and knows to render its template when that component is activated

    Component Classes with code

        - AuthLayout and MainLayout have empty classes
            export class AuthLayout {}
            export class MainLayout {}
            no code because they have nothing to do at runtime
            they are shell components — just render a navbar or sidebar plus <router-outlet>
            all logic lives in the HTML (static structure, no state, no subscriptions, no methods)
            the class must exist because Angular requires one — but it has nothing to do

        - Sidebar has code because it has runtime needs
            needs to know who is logged in → subscribe to currentUser$
            needs to show the user's name → store user as a property
            needs to respond to auth state changes → subscribe keeps user in sync
            needs a logout method → called from the template button click
            rule: if the component needs state, methods, subscriptions, or injected services → it has code
                if the component is purely static HTML structure → the class is empty

    Sidebar Subscription


        - this.sub = this.authService.currentUser$.subscribe(u => this.user = u)
            subscribes to the Observable exposed by AuthService's BehaviorSubject
            u => this.user = u  is the callback — runs every time a new value is emitted
            immediately runs with the current value (BehaviorSubject always emits current on subscribe)
            runs again whenever userSubject.next(something) is called anywhere in the app

        - what triggers it
            login()  → setSession() → userSubject.next(user)   → u = user   → this.user = user
            logout() → userSubject.next(null)                   → u = null   → this.user = null

        - the template reacts
            @if (user) { show name block }
            when this.user goes null → block disappears
            when this.user becomes a user object → name and username appear

        - why store in sub and unsubscribe
            sub is a Subscription object — a handle to the active subscription
            if the sidebar component is destroyed and you don't unsubscribe
                the subscription keeps running in memory forever → memory leak
            ngOnDestroy() { this.sub.unsubscribe() }
                runs when Angular removes this component from the DOM
                cleans up the subscription properly

    Form builder
    
        - inject(FormBuilder)
            FormBuilder is an Angular service — a helper for creating form structures
            inject() gets the singleton from Angular's DI container (same as inject(AuthService))

        - this.fb.group({ fieldName: [initialValue, [validators]] })
            creates a FormGroup — a container that manages a set of related form controls together
            each key = a field, each value = array of [startingValue, [validator functions]]
            FormGroup tracks for every field: current value, validity status, touched/dirty state
            form.value → { firstName: 'Thomas', lastName: 'Claiborne', ... }
            form.invalid → true if ANY field fails any validator
            form.valid → true only when ALL fields pass ALL validators

        - Validators
            functions that Angular runs on every keystroke and return null (valid) or an error object
            Validators.required    → fails if the value is empty
            Validators.minLength(3)→ fails if value.length < 3
            Validators.maxLength(30)→ fails if value.length > 30
            Validators.email       → fails if not a valid email format
            Validators.pattern('^[a-zA-Z0-9_]+$') → fails if value contains anything outside the pattern
            multiple in an array → all must pass for the field to be valid

        - f('username')?.hasError('minlength')
            f() is a helper method: return this.form.get(fieldName)
            .get() returns the FormControl for that field
            .hasError('key') checks if that specific validator failed
            used in the template to show different messages for different failure reasons
            the ?. is optional chaining — safely handles the case where the control doesn't exist

        - f('username')?.invalid && f('username')?.touched
            .invalid → at least one validator is failing
            .touched → user has clicked into and out of this field at least once
            combining them: only show the red border AFTER the user has interacted
            without .touched: every field shows as invalid the moment the form loads (bad UX)

        - loading property
            set to true before the HTTP call, false in the error callback
            [disabled]="loading" prevents the user from clicking submit again while waiting
            button text changes: 'Create Account' → 'Creating account…' via {{ loading ? ... : ... }}

        - error (Login) vs errors: string[] (Register)
            Login fails one way at a time: "Invalid credentials." — one message, one string
            Register can fail multiple ways at once:
                DTO validation from [ApiController] returns ALL failed fields simultaneously
                service can return username taken, email taken as separate messages
                string[] holds multiple messages and renders each in its own <div>
            register error handler:
                Array.isArray(err.error) → service returned ['Username is already taken.']
                err.error?.errors → [ApiController] returned ProblemDetails with { Field: ['msg'] }
                    Object.values(...).flat() flattens { Email: ['bad email'], Username: ['required'] }
                    into ['bad email', 'required'] — one flat array of all error strings

        - where errors render in the template
            @if (errors.length) block sits ABOVE the form fields
            only appears when the array has at least one item
            each string in the array gets its own <div> via @for
            disappears on next submit attempt because errors = [] resets it first

    Template Control flow

        @if (condition) { ... }
            renders the block only when condition is truthy
            condition is evaluated against the component's properties and methods
            replaces the old *ngIf="condition" syntax
            @if (error) { ... } @else { ... }  — else branch when needed

        - @for (item of list; track item) { ... }
            iterates over an array and renders the block once per item
            item is the loop variable — available inside the block as {{ item }}
            track item (or track item.id) tells Angular how to identify items for efficient DOM updates
                without track: Angular re-renders the entire list on every change
                with track: Angular only updates the items that actually changed
            replaces the old *ngFor="let item of list; trackBy: fn" syntax

    Inject() vs import

        - import at the top of the file
            import { AuthService } from '../core/auth.service'
            TypeScript-level — tells the compiler "this type exists at this path"
            creates NO instance, allocates NO memory, does NOTHING at runtime
            required for type checking and IDE autocomplete

        - inject(AuthService)
            private auth = inject(AuthService)
            Angular-level — asks Angular's DI container for the live instance of AuthService
            Angular looks up its registry, finds the singleton it already created, returns it
            if you called new AuthService() instead:
                you'd get a completely fresh instance with an empty BehaviorSubject
                no shared state, no connection to the session or other components
                defeats the entire point of a singleton service
            inject() gives you the same instance everyone else uses — the one with real state in it

        - both are always needed
            import → TypeScript can understand the type (compile time)
            inject() → you get the actual running instance (runtime)
            having the import without inject() = TypeScript knows the shape but you have no instance
            having inject() without the import = TypeScript doesn't know the type → compile error
